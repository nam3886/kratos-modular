# Repository Guidelines

Kratos modular-monolith boilerplate: one deployable application made of
modules that the compiler keeps apart. This file owns the architecture
contract agents must follow.

## Project structure

```
api/<module>/v1/          Proto (service, messages, error reasons, events) + generated stubs.
api/openapi/openapi.yaml  Generated API document.
cmd/server/               main.go, modules.go (module list), wire.go, integration test.
cmd/migrate/              Applies migrations to every configured database.
configs/config.yaml       The only configuration source. No secrets.
migrations/<database>/    Versioned SQL (goose) + atlas.sum; one dir per database, not per module.
internal/conf/            Config proto; generated by `make config`.
internal/server/          HTTP/gRPC servers, JSON codec, CORS, body limit, metrics, messaging.
internal/platform/        Shared infrastructure, no business logic: db, mq, migrate, testkit.
internal/module/<m>/      module.go + wire.go + internal/{service,biz,data}.
```

## Architecture rules

1. **Module boundary.** Everything under `internal/module/<m>/internal/` is
   importable only by `internal/module/<m>/`. Outside code (other modules,
   `cmd/`, `server/`) imports only `internal/module/<m>` and `api/<m>/v1`.
2. **Direct calls go one way.** If A calls B, B must not call A (Wire reports
   `cycle for ...`). The caller declares the interface it needs in its own `biz`
   and implements it in its own `data` over the other module's generated server
   interface (e.g. `payment/internal/data/settings_client.go`).
3. **The reverse direction is an event** via outbox + RabbitMQ. Delivery is at
   least once: handlers dedupe with the inbox (`mq.FirstTime`) in their own
   transaction.
4. **A transaction lives inside one repository method.** `biz` never sees a
   transaction. No cross-module transactions, even on the same database.
5. **Databases are shared infrastructure.** A module picks one with the
   `database` constant in its `data.go`; modules on one database share a pool.

A change crossing these rules the wrong way is a design bug; fix the design
rather than add the import.

## Layers inside a module (DTO / DO / PO)

```
client ──► DTO ──► service ──► DO ──► biz ──► DO ──► data ──► PO (Ent) ──► storage
```

- **service (proto ↔ biz).** Implements the generated server interface and
  handles incoming events. Converts proto to biz entities and back (the reply
  is built at the return site, or by a `reply()` helper when more than one
  handler shares it). Validation lives in `biz`, which returns the specific
  reason. Returns biz errors. No business rules, no Ent.
- **biz (DO only).** Owns entities, usecases, typed errors, and the repo
  interfaces it needs (including ones for other modules, such as `LimitReader`).
  Imports only its own `api/<m>/v1` (for error reasons). Never Ent, Watermill,
  or another module.
- **data (Ent ↔ biz).** Implements biz repo interfaces; constructors return the
  biz interface, never the concrete type. Ent types never leave `data`
  (`toBiz` / `new<Resource>` conversions). Publishes events and opens
  transactions here. Maps not-found to biz typed errors; any other error is
  returned as is and becomes `INTERNAL` at the server.
- **server.** Transport only: construct servers, middleware, register modules.
  A middleware logs every non-Kratos error and replies with `INTERNAL`, so
  driver text never reaches clients.
- **cmd.** The only place that wires modules together (`modules.go`, `wire.go`).

List endpoints use offset pagination with AIP filtering and ordering; copy
`ListPayments`. `service` declares the fields a client may filter and order on,
`data` translates them to Ent (`aip-go/ents`) and always adds `id` descending
as the last sort key.

An event published with `mq.Publish` carries the trace of the request; a
handler must use the `ctx` it is given for logging and queries.

## Adding a module

1. Write `api/<name>/v1/*.proto`, then `make api`.
2. Copy `internal/module/settings` (or `payment` if it consumes events) to
   `internal/module/<name>` and replace its contents; a module with consumers
   must also rename `data.Consumer` in its `data.go`.
3. Add the module to `cmd/server/wire.go` and `cmd/server/modules.go`, then
   `make ent wire`.
4. `make migration module=<name> name=<name>_init`, then `make migrate`.

## Changing the schema

1. Edit the module's Ent schema.
2. `make ent`
3. `make migration module=<module> name=<what_changed>` (add `db=<name>` if
   the module does not use `main`)
4. `make migrate`

Never hand-edit `atlas.sum`; hand-written goose files may share the directory.

Removing an entity does not drop its table: write the `DROP TABLE` by hand.
Declare every index in the Ent schema; one that is missing there is dropped by
the next `make migration`.

## Testing

Tests sit beside the code (`*_test.go`). No SQLite, no mock generators, no
architecture tests.

| Layer | How |
|---|---|
| `biz` | plain Go, hand-written fakes of repo interfaces |
| `service` | call service methods with real usecase + fake repo |
| `data` | real repository on `testkit.Postgres(t)` (Docker) |
| `server` | unit tests for codec, `bodyLimit` and the internal-error middleware |
| `platform/mq` | real PostgreSQL and RabbitMQ (Docker) |
| `cmd/server` (tag `integration`) | whole app via `wireApp` on real PostgreSQL + RabbitMQ |

## Workflow

- Subagents edit and commit only in their task's own worktree; never touch
  the main worktree or its git index.
- Subagents that write code run `go vet` on the packages they changed (plus
  `go test` when the package has tests) before reporting done.
- Gate before handoff: `go build ./... && go vet ./...`. When touching
  `api/`, `internal/conf/`, `internal/module/*/internal/data/ent/schema/`,
  or Wire providers, also run `make generate` then `git diff --exit-code` to
  catch generated drift.

## Generation & generated files

Regenerate via `make generate` (= `api config ent wire`) or
the single steps `make api`, `make config`, `make ent`, `make wire`. Never
hand-edit `*.pb.go`, `*_grpc.pb.go`, `*_http.pb.go`, `wire_gen.go`, Ent
output, `api/openapi/openapi.yaml`, or `atlas.sum`. `go.mod` carries
`tool entgo.io/ent/cmd/ent`: it pins `golang.org/x/tools` so `make ent` stays
reproducible under `go mod tidy`; do not remove it.

## Naming & error reasons

- Resource `<Resource>` (e.g. `Payment`); collection RPC `List<Resources>`.
- Types: repo `<Resource>Repo`, usecase `<Resource>Usecase`, service
  `<Resource>Service`. Conversions: convert inline at the boundary; extract
  `convert<Resource>` / `new<Resource>` / `toBiz` / a `reply()` helper only when
  more than one handler or repo method shares it.
- Error reasons: `ErrorReason` enum in `api/<m>/v1/<m>.proto`, surfaced as
  `Err<Resource><Cause>` in `biz`.

## Commits & security

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `chore(deps):`,
  `docs:`, `test:`. Regenerated files belong in the same commit as
  their source.
- Never commit real credentials in `configs/config.yaml`.
